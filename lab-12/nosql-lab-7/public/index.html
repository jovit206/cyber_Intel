MongoDB 5.0+ resharding notes

Resharding copies data to a new shard-key distribution, applies writes made during copying, and commits a consistency point. Before starting, confirm the supporting index, unique-index compatibility, healthy shards, spare disk and network capacity, and no active index build. Temporary copies consume resources; the commit phase can briefly block writes and cannot be aborted after commit begins. Hashed shard keys cannot be unique, and some specialized index/encryption workloads have restrictions. Resharding is not triggered from this dashboard.

How the advisor scores strategies

It starts from a neutral fit score, adds credit when a candidate matches selected query patterns, rewards compatible ordered ranges, accounts for entity-scoped reads, and adjusts for high write frequency on recent records. Large expected datasets add a small hashed-key preference when distinct values are available. Each adjustment and its reason is returned with the recommendation.

Planning guidance. Production choices require representative workload tests, cardinality and skew analysis, capacity planning, and evaluation of compound keys where queries combine an entity equality filter with a range such as time.
